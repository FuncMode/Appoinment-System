- **Petsa:** 2026-09-15
- **Reference:** [miqdadbadjuber/anti-slop](https://github.com/miqdadbadjuber/anti-slop) (`antislop.md`, Mode 2 audit), method mula sa `audit-001-2026-09-15.md`
- **Saklaw:** Lahat ng 11 patient portal screens — Dashboard, Find a doctor (Doctor Listing), Doctor Availability, Book Appointment, Booking Confirmation, Appointment Status, Appointment History, Appointment Details (+ Reschedule Modal, Cancel Modal), Profile, Medical Records, Help & Support — kasama ang shared portal shell (`AppShell`, `Sidebar`, `Topbar`/notifications, `PageHeader`, `Modal`/`ConfirmModal`, `Pagination`, `Field`/inputs, `EmptyState`/`ErrorState`, `ToastLayer`) at ang portal sections ng `styles.css`. ## HIGH — Hard Gate (absolute rules)

**1. R-26 + R-32 — Ang buong sidebar navigation ng portal ay hindi keyboard-operable.**
`components.jsx` ~197-203 at ~207-211: ang `.sidebar-item` (Dashboard, Find a doctor, Book appointment, My appointments, Medical records, Profile, Help & support) ay clickable `<div onClick>` lang, walang `role="button"`, `tabIndex`, o Enter/Space handler. Hindi maabot ng Tab ang **buong primary navigation ng portal**, desktop at mobile drawer (`AppShell` gumagamit ng parehong `Sidebar`, `components.jsx` ~366). Mas malala kaysa sa `.demo-account` issue ng audit-001 (#3) dahil ito ang nav mismo, hindi isang helper control. Ironic pa: may existing `.sidebar-item:focus-visible` rule sa `styles.css` ~275, pero dead rule ito dahil hindi naman focusable ang element. Contrast: ang `.doctor-card` at `.list-item` sa loob ng portal ay tama (`role="button"` + `tabIndex={0}` + `activateOnKey`, `screens-patient.jsx` ~25-32, ~308-317, ~449-458).

**2. R-26 + R-32 — Ang breadcrumb links sa `PageHeader` ay `<a>` na walang `href`.**
`components.jsx` ~636: `<a onClick={() => navigate(b.to)}>{b.label}</a>`. Walang `href` = hindi nasa Tab order, hindi ma-activate gamit ang keyboard, walang pointer cursor, at hindi right-click/middle-click-able. Ginagamit ito ng halos lahat ng portal pages (Status, History, Details, Profile, Records, Help). Ang tamang anyo: `<a href={'#' + b.to}>` o `<button>`.

**3. R-36 — Mga gawa-gawang operational claims sa booking flow (SMS at email).**
Walang backend/notifications ang prototype, pero:
- `screens-patient.jsx` ~881 (Booking form info card): `"You'll receive an SMS confirmation within 15 minutes."` — walang SMS na nangyayari.
- `screens-patient.jsx` ~882: `"Cancellations must be made at least 4 hours in advance."` — **kontradiksyon sa totoong behavior**: walang 4-hour check kahit saan; ang cancel (History at Details) ay nagko-confirm agad, kahit anong oras/distance.
- `screens-patient.jsx` ~909 (Booking Confirmation): `"We've sent a confirmation to your email."` — walang email backend.
- `screens-patient.jsx` ~1054 (Status timeline): `'Confirmed · SMS sent'` — nagsasabing "SMS sent" kapag confirmed; imaginary pa rin.
Ito ang katumbas ng "encryption in transit" claim na inayos sa Privacy page (audit-001 #5): fictional na ospital OK, pero mga spesipikang pang-operations na hindi nangyayari = dishonest copy. Ayusin sa (a) tanggalin/palitan ng totoo ("You'll see the status update in this portal"), o (b) i-label bilang production-system intent.


**4. R-36 — FALSE na security claim sa Help & Support FAQ.**
`screens-patient.jsx` ~1826: `"Are my records and data secure?" — "Yes. Data is stored in access-controlled systems, passwords are only kept as secure hashes, and this prototype only uses fictional demo data."` — Ang "passwords are only kept as secure hashes" ay **mali**: plain-text passwords sa `localStorage` (`components.jsx` ~77, ~1611). Ang parehong claim ay na-flag at inayos na sa Privacy page (audit-001 #5), pero may natira pa rito sa portal Help page. High stakes dahil health records ang context.

**5. R-02 — Mga em dash (`—`) na natira sa portal UI text (±10 instances ng punctuation; hindi saklaw ang audit-001 fix na public pages lang).**
- ~146 (Dashboard empty state): `"No upcoming appointments — your schedule is clear."`
- ~784 (Booking doctor dropdown): `{d.name} — {d.specialty}`
- ~824 (Booking notes help): `"Optional — anything else the doctor should know."`
- ~1824 (Help FAQ): `"Pending — your request was received… Confirmed — your slot is reserved. Completed — the visit has happened. Cancelled — the appointment was called off."` (apat sa isang answer)
- Downloaded artifacts (UI text din ito ng user, nasa file):
  - ~81 (receipt title): `Receipt APX001 — MedicaCare`
  - ~96 (receipt disclaimer): `"Prototype receipt — fictional data for demo purposes only."`
  - ~68, ~70 (ICS file): `SUMMARY:Dr. X — Cardiology`, `DESCRIPTION:… — reason`
*(Ang em dash sa code comments ay exempt — hindi UI text. Ihiwalay ang `'—'`-as-empty-placeholder, tingnan ang #17.)*

**6. R-03 — `.btn.sm` ay nananatiling 30px sa mobile.**
`styles.css` ~242: `.btn.sm { height: 30px; }` — mas mataas ang specificity ng `.btn.sm` (2 classes) kaysa sa mobile override na `.btn { height: 44px; }` (~1485), kaya **hindi umaabot ng 44px sa mobile** ang "View profile" / "Book" buttons sa loob ng doctor cards (Doctor Listing). Desktop ay OK (pointer context); mobile lang ang violation.

**7. R-03 — Help & Support FAQ accordion buttons ay ~20px lang ang tap target.**
`screens-patient.jsx` ~1870: inline `style={{ background: 'transparent', border: 0, padding: 0, … }}` sa accordion question button. Iba ito sa public `.faq-question` (~48px, PASA sa audit-001); itong portal inline version ay text-height lang (~20px), malayo sa 44px.

**8. R-03 — `.toast-close` ay hindi tap-target size (at walang mobile override).**
`components.jsx` ~767 + `styles.css` ~628: `padding: 0`, walang width/height, 14px icon lang ang hit area (~14×14px). Walang entry sa mobile 44px media query (~1483). Katumbas ito ng `.testimonial-dot` issue ng audit-001 (#2).

**9. R-03 — `.page-btn` (pagination) ay 30px, ginagamit sa mobile.**
`styles.css` ~517-518: `min-width: 30px; height: 30px;`. Ginagamit ng Appointment History pagination at ng mobile Doctors pager. Walang 44px mobile override. *(Honesty note: hindi ito nahuli sa audit-001 kahit nandoon din ito sa public mobile doctors pagination, pasensya na.)*

## MEDIUM — Purpose-Gate (allowed, pero kailangan ng nakasulat na dahilan)

**10. R-17 + R-38 — Doctor ratings at "years of experience" na naka-present bilang totoo sa loob ng portal.**
Doctor Listing card: star icon + `{d.rating}` + `{d.exp} yrs` (~471); availability page at doctor profile modal: `"Rating 4.9 / 5.0"` (~536-537). Mula sa seed data, walang rating system sa app, at **wala nang visible fictional disclaimer sa loob ng portal shell** (ang footer disclaimer ay public-pages lang). Sa marketing page ito ay naka-mitigate ng disclaimer; dito sa working app UI, malinis na "fakts" ang itsura. Ito rin ang rating scale na tinanggal sa Landing stats ("4.8 / 5") sa audit-001 #4, pero ang per-doctor version ay nananatili rito at sa public Doctors page. Mabigat ang timbang dahil medical trust ang usapan.

**11. R-23 — randomuser.me portraits sa loob ng portal, walang honesty label.**
Ang public Doctors page ay may visible na "placeholder portraits, not real staff" label pagkatapos ng audit-001 (#10), pero ang portal Doctor Listing / Availability / Dashboard ay walang katumbas. Parehong dummy portraits (`data.js` doctor `photo` fields). Ang Medical Records page lang (~1809) at Profile (~1541 comment + note) ang may sariling fictional notes.

**12. R-25 — Contrast: date-chip secondary text sa Doctor Availability.**
`styles.css` ~603-610: weekday (11px) at month (10px) labels na `color: var(--text-secondary)` + `opacity: 0.7` sa puting chip. Blended ≈ #7E8896 sa white ≈ **3.6:1**, hindi umaabot sa 4.5:1 para sa maliit na text. Ang 18px day number (opacity 0.9 sa `--primary`) ay ≈ 4.7:1, borderline-pass. Ang mga chip na ito ang primary booking input ng app, kaya mas mahalaga kaysa decorative.

**13. R-32 — Modal: walang focus management.**
`components.jsx` ~727-748 (`Modal`, ginagamit ng Reschedule/Cancel atbp.): may Escape at scrim-click close (mabuti), pero walang `role="dialog"`/`aria-modal`, walang initial focus, walang focus trap, at hindi ibinabalik ang focus sa trigger pagkatapos magsara. Ang keyboard user ay nakakapag-Tab palabas ng bukas na modal papunta sa background page.

**14. R-08 — "Continue" CTA arrow sa Availability.**
`screens-patient.jsx` ~641: `Continue <Icon name="arrow-right" />`. Ang audit-001 ay nag-alis ng decorative arrows sa lahat ng CTA; ito ang natirang CTA-arrow sa portal. May hinaang depensa (multi-step flow, "next step" meaning), pero kung ia-align sa naisulat na polisiya ng audit-001, tanggalin din. *(Ang breadcrumb chevrons ~634 at `.list-item` chevrons ~309/~1130 ay may totoong navigation meaning, PASA.)*

**15. R-37 — `DESIGN.md` may dials na, pero hindi pa nito iniuwirat ang portal-specific decisions.**
Ang Design Read/Dials (ENERGY 1 / RHYTHM 2 / MOTION 1) ay tinatakpan ang "patient portal" sa pangkalahatan, pero walang nakasulat na: (a) portal screen rhythm (banner + stats + list pattern ng Dashboard), (b) per-doctor rating/star motif policy (#10), at (c) portal portrait policy (#11). Isang kabanata lang ang kulang.

## Addendum: Automated Click-Through (2026-09-15, R-35)

Gumawa ang agent ng `frontend/scripts/clickthrough.mjs` — dev-only, **zero npm
dependencies** (Node 18+ built-in fetch/WebSocket + system Chrome/Edge via
DevTools Protocol) — para Maisagawa na ang click-through na hindi kayang gawin
nang manual sa environment. Ini-s.Serve ang production build (`vite preview`)
at hinawakan ang app sa headless browser sa dalawang viewport.

**Saklaw ng bawat viewport (desktop 1280×800, mobile 390×844):** real login sa
demo account → Dashboard (quick actions, notifications, mark-all-read) →
sidebar/drawer navigation → Doctor Listing (honesty label, search, specialty +
availability filters, View profile modal, Book) → Availability (date chip, slot
chip, Continue, Cancel) → Booking form (empty-submit validation, valid submit) →
Confirmation (reference number, actions) → Status (timeline, details link) →
History (search, status filter, sort, row actions) → Details (receipt +
.ics downloads, reschedule modal na may totoong paglipat, cancel confirm "Keep
it") → Profile (edit + save, wrong-password inline error) → Records (fictional
note, table) → Help (lahat ng FAQ accordions, honest security answer) → Logout
→ Admin sanity check (demo login, sidebar, live pending badge, logout).

**Resulta:** 52/52 actions PASSED, zero console/page errors, zero horizontal
overflow sa lahat ng screens sa parehong viewport.

**Mga natutunan sa pagda-run (walang app bug na nahanap; lahat ay test-script
issues na inayos rin):**
- Ang mga toast ay 3.8s ang buhay — ang `waitFor('.toast')` sa reschedule step
  aydating tumatama sa naiwang download toast; pinalitan ng paghihintay sa
  pagsasara ng modal.
- Ang reschedule modal ay tama lang na naka-disable ang "Save new schedule"
  kapag ang piniling date+slot ay ang kasalukuyang slot ng appointment
  (no-op reschedule guard) — kailangan pumili ang test ng ibang date.
- Sa mobile, ang sort header (`.th-sort`) ay hindi visible sa stacked table
  view — desktop-only affordance ito, hindi dead control (ang pag-sort ay
  available pa rin sa desktop).

**Patakbuhin:** `npm run build` + `npx vite preview --port 4179 --strictPort`
(terminal 1) + `node scripts/clickthrough.mjs` (terminal 2).
